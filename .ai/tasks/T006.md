## Objective
The UI built on the `ui` branch (inspection-report design: `src/components/*`, `/scan`, `/playground`) is now merged into `main`, but it runs on mock data (`USE_MOCKS = true` in `src/components/api-client.ts`) and was written against the T001 API. Make it work end to end against the real stateless API from T002-T004 so a judge on the live site can: pick the demo bot (or paste their own prompt), run a quick scan with live progress, see the A-F report, click "Fix my chatbot", re-test at L1 and L2, and see the before/after improvement. This is the live demo for the hackathon; it must be stable on a slow, rate-limited LLM key.

## Required Context
- `AGENTS.md` (design section), `docs/api-contract.md`
- `src/lib/types/*.ts` (the zod schemas are the source of truth), `src/app/api/**` route handlers (read only)
- `src/components/*` and `src/app/{page,layout}.tsx`, `src/app/scan`, `src/app/playground`
- `src/mocks/*` and `src/components/mock-data.ts`
- `eval/smoke-demo.mjs` (it shows the exact client-side call sequence: plan -> steps with the returned concurrency -> finalize -> fix -> retest)

## Acceptance Criteria
1. **Real API by default.** `USE_MOCKS` is false unless `NEXT_PUBLIC_USE_MOCKS=true`. `api-client.ts` calls `POST /api/scans`, `/api/scans/step`, `/api/scans/finalize`, `/api/fix`, `/api/demo-bot/chat` with request/response bodies that parse with the current zod schemas (import the schemas/types from `src/lib/types`; no duplicated hand-written types). Responses are validated; a non-2xx or invalid body becomes a typed UI error, never a crash.
2. **Scan flow** (`/scan`): target choice = demo bot (Zara Fabrics) or "paste your own system prompt" + protected values (comma/line separated); quick (30) or full (60); runs steps from the browser using the `concurrency` the plan returns; live progress (n/total, current attack id + language, running breach/pass/error counts); a Cancel button that stops issuing new steps; then finalize and show the report card.
3. **Report card** shows grade, score, severity-weighted ASR, breakdown by language (English / Urdu / Roman Urdu) and by intent, and the list of findings with the fixed bilingual text (EN + UR), evidence redacted as the API returns it. Errors are shown as errors with their plain-language cause (e.g. rate limited) and an explicit note that errors are not counted as passes. If more than 30% of steps errored, show a clear banner: results incomplete, try again in a minute.
4. **Fix and re-test**: "Fix my chatbot" calls `/api/fix` with the scan's findings at level 1; show the hardened prompt (collapsible) and `changes_en` / `changes_ur`. "Re-test (L1)" runs a new scan with `level: 1, kind: "retest", fix`. Then offer "Add output guard (L2)" -> fix at level 2 -> re-test. A **before/after** panel shows L0 -> L1 -> L2 grades and scores side by side with the change in breaches. State is kept in the page (no database).
5. **Sample report**: a "View sample report" entry (landing page and /scan) renders a complete L0 -> L1 -> L2 example from a static fixture, clearly labelled "Sample run - recorded data", so judges can see the full story even if the AI provider is rate-limiting. Build the fixture from `src/components/mock-data.ts` (or `src/mocks`), shaped to the current schemas and validated by a test. Do not label mock data as live.
6. **Playground** (`/playground`): chat with the demo bot at L0, L1 or L2 via `/api/demo-bot/chat`, with errors shown inline.
7. **Landing page** (`/`): replaces any starter content; product name Bizvyra, "by Team HackForge", tagline "Detect. Fix. Protect. Prove.", one-sentence problem statement, primary action "Scan the demo chatbot", secondary "View sample report", and a short how-it-works strip (scan, grade, fix, re-test). Keep the existing inspection-report visual language from `AGENTS.md`; no new design system.
8. **Quality floor**: works at 360 px width and desktop; visible keyboard focus; buttons disabled while a request is in flight; `prefers-reduced-motion` respected; Urdu text uses `dir="rtl"` and `lang="ur"`; no console errors in the happy path.
9. **Tests** (Vitest, fetch mocked): api-client request bodies and response parsing for all five routes; error mapping (429/500/invalid JSON); the sample fixture validates against the schemas; the scan runner honours concurrency and cancel. No test reaches a real provider.
10. All four test commands exit 0; report gives exit codes, durations, raw log paths and exact Vitest counts. Note any route/schema mismatch you found and how the client handles it.
