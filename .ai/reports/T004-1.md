## Acceptance criteria and evidence

### C1: adapter retry, backoff, Retry-After, budget, no retry on 4xx, error kind

**Implementation** (`adapter.ts`):

- `chat()` loops over `attempt()`.
- `attempt()` returns either `{ done }` or `{ retry, retryAfter }`. Retryable outcomes are a status in `RETRY_STATUSES = {429, 500, 502, 503, 504}`, or a fetch rejection when the signal was not aborted (a network failure before a response).
- After `LLM_MAX_RETRIES = 3` retries, the last failure is returned.
- `retryDelayMs(retry, retryAfter)`:
  - Delta seconds: `/^\d+(\.\d+)?$/` × 1000.
  - An HTTP date (starts with a day name) gives `max(0, date − now)`.
  - Otherwise `1000 × 2^retry × (0.75 + random × 0.5)`.
  - The result is always `min(…, 10 000)`.
- Budget: `deadline = start + 30 s`. Each attempt's timeout is `min(15 s, deadline − now)`. A retry runs only when `now + wait + 2 s ≤ deadline`; otherwise `{ ok: false }` is returned with the last failure.
- Timeouts and every status other than these five return at once.

**Tests** (`adapter.test.ts`, "retry, backoff and error kinds (T004)", fake timers, `Math.random` fixed at 0.5; all pass in F3):

- **Backoff and retry cases:**
  - 429 then success: 1 call at 999 ms, 2 at 1000 ms, then `{ ok: true }`.
  - A network failure is retried.
  - 503 on every attempt: calls at 0 / 1 / 3 / 7 s, exactly 4 in total, never a 5th. The result is `{ code: "http", kind: "unavailable", status: 503 }`, and it contains neither the key nor the provider body.
  - 503 three times, then success on the last retry.
  - HTTP 500, 502 and 504 are retried.
- **Retry-After:**
  - `Retry-After: 3` gives a wait of exactly 3000 ms.
  - An HTTP date 5 s ahead gives exactly 5000 ms.
  - `Retry-After: 120` is capped at 10 000 ms.
- **No retry on 400, 401, 403 or 404:** each makes 1 call, with kinds `bad_request`, `auth`, `auth`, `bad_request`. A timeout is not retried (one 15 s attempt).
- **Total budget:**
  - With `Retry-After: 10` each time, attempts run at 0, 10 and 20 s, and the call settles at 20 s with `rate_limited`, which is within 30 s.
  - With slow 503s (12 s each), the call settles at exactly 30 000 ms and not 1 ms earlier, after 3 attempts. The last attempt is cut by the budget (`timeout`).
- `retryDelayMs` unit cases:
  - jitter bounds 750/1500/3000 and 1250/2500/5000
  - seconds `"2"`, `"0"`, `"1.5"`; `"11"` capped
  - future, past and far-future dates
  - `"soon"`, `"-5"` and `""` fall back to backoff
- The `/api/fix` route test (`routes.test.ts`) checks end to end that HTTP 500 and network errors make 4 fetch calls and still return the deterministic fix.

## Problems and open questions

1. **`maxDuration` changes.** The contract does not ask for these, but without them the retry budget could exceed the old 60 s (step) and 30 s (fix) limits, and the platform would stop a valid request before it returns an error finding or the fallback fix. I did not check whether 120 s is within the limit of the Vercel plan in use; please confirm it before deploying.
2. **Worst-case step time.** At L2, one step can now take up to about 90 s on a heavily rate-limited key. With `SCAN_CONCURRENCY=1`, a 30-step quick scan can be slow, but it finishes with results instead of instant errors.
3. **Rate limiting can still win.** Retries do not raise the provider's quota. If a free-tier key's per-minute quota is far below the scan rate, some steps can still end as `rate_limited` errors, now labelled as such. A live re-run of `eval/smoke-demo.mjs --concurrency 1` with `LLM_REASONING=off` is the owner's step; it was not run here, per the restrictions.
4. **Gemini Pro.** `thinkingBudget: 0` applies to Gemini Flash models. Gemini 2.5 Pro cannot switch thinking off and would answer 400 (`bad_request`, not retried). This is noted in `.env.example` and the README.
5. **Retry-After numbers.** A decimal value such as `1.5` is accepted, which is more lenient than the RFC's integer form. Negative or garbage values fall back to backoff.
