Run id: `T003-2-fa2f`. Baseline: HEAD `1eef12b` (the attempt-1 work, committed by the owner).

## Summary

Attempt 1 failed verify on two checks:

- **test_commands:** in `src/core/http/routes.test.ts`, the test "POST /api/fix works for a prompt-mode target and rejects invalid input with 400" timed out at 5000 ms (`.ai/verify/T003-1-304a/cmd-3.log`).
  - **Cause:** the test did not stub the LLM environment or `fetch`. When the verifier's environment had LLM keys and `MODEL_STRONG` set, `/api/fix` ran the real refinement call through the real adapter (15 s timeout) and reached a real provider.
  - The first `/api/fix` test had the same weakness. It blanked `LLM_PROVIDER` and `MODEL_STRONG` but left `LLM_API_KEY` set and `fetch` unstubbed.
- **scope:** `docs/tasks/T004.md` was outside `allowed_files`. The owner committed it in `1eef12b`, so it is part of this attempt's baseline. This attempt does not touch it.

**Fix (test code only, no product change).** I added the same file-level hermetic guard to every test file that calls `/api/fix` or `/api/scans/step`:

- `src/core/http/routes.test.ts` (all `/api/fix` tests)
- `src/modules/chatbot/step-route.test.ts` (step-route tests)
- `src/core/security/usage.test.ts` (step-route rate-limit tests)

The guard:

- `beforeEach`: `vi.stubEnv(name, "")` for `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_REASONING`, `MODEL_FAST`, `MODEL_STRONG` and `MODEL_JUDGE`. It also replaces `fetch` with `vi.stubGlobal("fetch", fetchGuard)`, where `fetchGuard` throws "unexpected network call in a hermetic test".
- `afterEach`: `expect(fetchGuard).not.toHaveBeenCalled()`. The adapter catches fetch errors and turns them into typed errors, so this assertion is what makes a stray network call fail the test instead of being silently absorbed.
- `vitest.config.ts` already sets `unstubEnvs: true` and `unstubGlobals: true`, so both stubs are undone after each test.
- The test "never returns 500 when the LLM refinement fails" still sets its own provider env and its own failing `fetch` stubs, which override the guard. It never calls `fetchGuard`, so the `afterEach` check holds.

`step-route.test.ts` and `usage.test.ts` already mock `@/core/llm/adapter` with `vi.mock`. The guard adds defence in depth there: if that mock is ever removed, no real call can happen.
