## Summary

The inspection-report UI now runs on the real stateless API by default. Mock mode is opt-in through `NEXT_PUBLIC_USE_MOCKS=true` at build time.

- **API client** (`src/components/api-client.ts` plus `src/lib/ui/http.ts`): all five routes use the shared zod schemas from `src/lib/types`. The request is validated before it is sent and the response after it arrives. Every failure comes back as a typed `UiError` with a plain-language message and is never thrown. Failures covered: non-2xx, 429 with Retry-After, usage_limit, invalid JSON, wrong shape, network, timeout, cancel. The old hand-written request/response types are gone.
- **Scan runner** (`src/lib/ui/scan-runner.ts`): the browser makes three kinds of call: plan, then the steps (as many at once as the plan's `concurrency` allows), then finalize.
  - Cancel stops issuing new steps and aborts the ones in flight.
  - A step that fails at the HTTP level is retried: at most 2 times, waiting Retry-After or 2 s / 4 s, capped at 10 s. After that it is recorded as a schema-valid `error` Finding, never as a pass.
  - If finalize fails, the UI keeps the findings and offers "Retry scoring".
- **Scan flow** (`/scan`):
  - Setup: choose the demo bot or paste a prompt, with protected values separated by commas or lines.
  - Run: quick or full, with a live feed showing n/total, the attacks in flight with their language, running counts (✕ breach, ✓ pass, ! error), a rate-limit wait note, the log and Cancel.
  - Results: the report card, then "Fix my chatbot" (L1), "Re-test (L1)", "Add output guard (L2)" and "Re-test (L2)".
  - A before/after panel compares L0, L1 and L2. Level tabs switch between reports.
  - All state stays in the page; nothing goes to a database.
- **Report card**:
  - Grade, score, severity-weighted ASR and counts, with the note that errors and skipped tests are not counted as passes.
  - Tables by language and by intent.
  - Findings grouped by intent, plus every finding in EN and UR. Each finding shows the redacted evidence, prompt and reply exactly as the API returned them.
  - A "Results incomplete … try again in a minute" banner when more than 30% of steps errored, naming the most common cause.
- **Sample report** (`/report/sample`, linked from the landing page, `/scan` and the navbar): the full L0→L1→L2 run from the static fixture `src/lib/ui/sample-run.json`. It is labelled "Sample run - recorded data", with a second line saying it is illustrative and not a live scan.
- **Playground**: has a level selector and shows errors inline (the message goes back into the input box). L1 and L2 are disabled: see C6 and Open question 1.
- **Landing page** (`/`):
  - New hero: "Bizvyra by Team HackForge", the tagline "Detect. Fix. Protect. Prove." and a one-sentence problem statement.
  - Buttons "Scan the demo chatbot" and "View sample report".
  - A four-step "How it works" strip (Scan, Grade, Fix, Re-test).
  - The F→C→B grades come from the fixture and are labelled as sample.
- **Quality**:
  - A global `prefers-reduced-motion` rule.
  - Every button is disabled while its request runs.
  - Urdu text always carries `lang="ur"` and `dir="rtl"`.
  - Dates render in UTC, so server and client render the same output.
  - The fixture is loaded lazily in mock mode only, so live `/scan` does not ship it.
- `.env.example` documents `NEXT_PUBLIC_USE_MOCKS`.

## Route/schema mismatches found and how the client handles them

1. **`/api/demo-bot/chat` cannot chat at L1 or L2.** It accepts `{ messages }` only and always uses the original demo prompt. The client offers L0 only and explains why. This is the C6 FAIL.
2. **The step response does not carry the attack's `severity` or `standard`.** The client needs them when it records a step whose HTTP request failed. It records `severity: 1` and `standard: "n/a"` for those client-side error findings. Errors carry no weight in scoring, so the score does not change. The evidence says the test did not run and is counted as an error, not a pass.
3. **The scan response carries no severity-weighted ASR.** The UI computes it from the findings with the contract formula. A test checks it against the API score.
4. **Leading assistant messages.** The playground used to send its greeting as the first message. The greeting is page text, so it is no longer sent, and the conversation sent to the bot starts with the customer. This is not a schema problem, but some providers reject a history that starts with the assistant.
