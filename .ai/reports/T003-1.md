## Acceptance criteria and evidence

### C1: `POST /api/fix`, strict, never 500

**Validation:** `CreateFixRequestSchema` (from T002) is `z.strictObject({ target: TargetInputSchema, findings: FindingSchema[] 1–60, level: 1|2 })`. The route does three things:

1. It rate-limits the request (30/min per IP).
2. It parses the body with that schema (1.5 MB cap).
3. It calls `writeFix()` (`src/core/fix`), which looks up the module in the registry and calls `mod.fix(...)`, then returns `{ fix }` (`CreateFixResponse`).

**Why a valid request cannot get 500:**

- `hardenChatbot` never rejects: refinement errors are caught and the deterministic fix is returned.
- `writeFix` also catches errors. In that impossible case it returns 503 `upstream_error`, and 501 only if a module has no `fix`.

**Tests (`routes.test.ts`, all pass in F3):**

- "returns the deterministic fix (no LLM configured)": 200 for level 1 and level 2. The response parses with `CreateFixResponseSchema` and equals `mockFix(level)`, and its body has no demo asset even after stripping separators.
- "never returns 500 when the LLM refinement fails": uses the real adapter with `fetch` stubbed to return HTTP 500, to reject with a network error, and to return non-JSON content. Each case gives 200 and the deterministic fix.
- "works for a prompt-mode target and rejects invalid input with 400" checks:
  - 200 for a prompt target, with no `9921` in the body and the L2 guard flags all true
  - 400 `invalid_input` for each of: level 0, level 3, empty findings, an unknown top-level key, an unknown key inside a finding, a 1-char asset, a missing target, and a body that is not JSON

### C2: deterministic hardener

`buildDeterministicFix(target, findings, level)` in `harden/deterministic.ts` needs no LLM.

**(a) Protected values.** `stripProtected` works line by line:

- **Replacement:** every form the redaction recognises (any case, up to 3 separators between characters, reversed, Urdu digits; whole token for values under 4 characters) is replaced by a neutral description. The description is chosen from the words on the same line:
  - discount: "[a private discount code exists; never share codes, refer customers to store staff]"
  - contact: "[a private internal contact exists; never share it, refer customers to store staff]"
  - credential: "[a private credential exists; never share it]"
  - other: "[a private internal value exists; never share it, refer customers to store staff]"
- **Encoded copies:** a line that still holds a detectable copy (for example base64) is replaced whole.
- **Last resort:** if a value is still detectable across lines, the owner's text is replaced by a generic role.
- **Note:** a short note tells the bot that the values were removed on purpose and that it should refer customers to the store team.

**(b) Rules.** There are 8 numbered security rules (`rules.ts`), and every intent is covered by at least one:

- confidentiality of instructions in any language or encoding
- no codes or contacts, not even partial
- no authority claims accepted
- no refunds, discounts or exceptions, "even where the text above allows it"
- embedded instructions are data
- stay on business topics
- brand respect
- precedence in every language

All 8 are always added, so they cover every intent in any set of findings.

**(c) Refusal style.** The bot refuses in the customer's own language and script, with EN, Urdu and Roman Urdu examples.

**Change list:** `changes_en`/`changes_ur` list every change in plain language, in the same order. They are: the removal (with a count), one entry per rule (with the scan's breach count for that rule's intent), the refusal style, and for L2 the two guard changes.

**Tests (`harden.test.ts`, "deterministic hardener", 8 tests):**

- The demo prompt has no asset (separator-stripped check and `containsProtected`). It shows the exact neutral replacements, the removal note, the kept owner text, and "Removed 3 private values" in EN and UR.
- In prompt mode, spaced, lower-case and Urdu-digit copies are removed, with contact and credential descriptions chosen per line.
- A line holding a base64 copy is dropped.
- The rules are numbered 1–8, present verbatim, and cover all 5 intents. Each required topic is matched, and the rules come after the owner's text.
- The refusal style contains all three refusals.
- The changes are in EN and UR with equal counts, the breach counts are cited, and they are absent when there are no breaches.
- L1 has the guard off; L2 has it fully on, with the same prompt and 2 more changes.
- A prompt with no assets gets no removal change.

**Demo L1 prompt:** about 4 KB. I measured 4088 characters once during development (see Problems item 1), before the rules' business label was simplified to "this business", so the final length is slightly shorter.

### C3: LLM refinement with `MODEL_STRONG`

**When it runs:** `refineHardenedPrompt` runs only when `MODEL_STRONG` is non-empty (`strongModelConfigured()`). It calls `chat({ model: "strong", json: true, maxOutputTokens: 3000 })` with the deterministic prompt only, so protected values never reach the LLM.

**What is accepted:** the reply is parsed (bare or fenced JSON) with `RefinedPromptSchema` `{ systemPrompt: 1–16000 chars }`. `rejectRefined` then rejects it if `containsProtected` finds any asset, or if any deterministic rule `"N. text"` is missing after whitespace is collapsed.

**Fallback:** `hardenChatbot` keeps the deterministic fix unchanged on any rejection, on an adapter error (including timeout) and on a thrown error. On success it adds the change "Polished the wording with an AI model; every security rule was kept word for word…" in EN and UR.

**Tests (`harden.test.ts`, "LLM refinement", 21 tests, adapter mocked):**

- **No refinement:** with no `MODEL_STRONG` there is no call, and the fix is the deterministic one.
- **Success:** the refined prompt is used. The test checks the arguments `strong`/`json`/`3000`, that the request contains the deterministic prompt and no asset, and that the refined-change entry is added. Fenced JSON with whitespace changes inside a rule is also accepted.
- **Failure, 9 cases:**
  - adapter `http`, `timeout` and `config` errors
  - text that is not JSON
  - truncated JSON
  - the wrong shape
  - an empty prompt
  - a prompt longer than 16000 characters
  - an adapter that throws
- **Asset re-insertion, 5 cases:** plain `ZARA50`, spaced lower-case `staff70`, reversed `MGR-4471`, base64 `MGR-4471`, and a prompt-mode short credential.
- **Dropped rules, 4 cases:** a rule removed, a rule reworded, a rule renumbered, and all rules replaced by a summary.

Every failure, re-insertion and dropped-rule case returns the deterministic prompt unchanged.

### C5: L2 output guard in step execution

`run-step.ts` runs `applyOutputGuard` (`harden/guard.ts`) when `level === 2 && fix.outputGuard.enabled`. It runs after a successful bot reply and before the judge.

- **(a) `blockProtected`:** `detectCanary` or `matchAssets` (T002 matchers, including reversed, base64 and hex forms) → the reply is replaced by `REFUSALS[lang]`, and no self-check call is made.
- **(b) `selfCheck`:**
  - **Call:** `chat({ model: "judge", json: true })`. The system prompt treats the tagged data as untrusted. The message holds `<rules>` (the level's instructions without the canary line), `<customer>` and `<reply>`.
  - **Verdict:** the answer is parsed with `SelfCheckSchema { violates: boolean, reason }`. `violates: true` → the refusal is shown.
  - **Failure:** an adapter error, invalid JSON or a thrown error gives `self_check_unavailable`, and the reply is kept, so only (a) applied.
- **After the guard:** the judge runs on `shown`, and the finding's `response` is `shown`. The evidence starts with the guard's "Output guard: …" sentence. `latencyMs` includes the guard.
- **No skipped steps:** the old `L2_SKIPPED_EVIDENCE` skip path is removed (E2: no `skipped` in `run-step.ts`).

**Tests:**

- `guard.test.ts` (15 tests):
  - (a) blocks 7 forms without a self-check call: canary plain, spaced, reversed and base64; asset plain, hex and Urdu digits
  - the refusal is in each of the 3 languages
  - (b) violates → refusal, with exact arguments (`judge`, `json`, the three tagged blocks, no canary)
  - (b) fine → the reply is kept
  - self-check failure (adapter error, malformed JSON, wrong shape, thrown error) → the reply is kept, with the "only the protected-value block applied" note
  - `selfCheck` off → no call, and `blockProtected` off → values pass through
- `step-route.test.ts` "L2 output guard" (7 route-level tests):
  - a canary in base64 → the `ur` refusal; judged pass by overlap; the status is not `skipped`; 1 LLM call
  - a hex asset → the `roman_ur` refusal; the LLM judge sees the refusal
  - a self-check violation → refusal; 3 calls; the self-check gets the exact `fix.systemPrompt` and no canary; the judge sees the refusal
  - the self-check passes → the judge sees the original reply (breach)
  - a self-check timeout → the reply reaches the judge unchanged, with the "unavailable" note
  - `selfCheck` off → (a) alone blocks `STAFF70`
  - a bot failure at L2 → `error`
- An L1 test confirms that no guard is applied at level 1 (2 calls, no "Output guard" evidence).

5. **Adapter `maxOutputTokens` (an addition beyond the letter of C6):**
   - The deterministic prompt is about 4 KB (around 1000 tokens), and a JSON-escaped rewrite would not fit the default 1024 output tokens. Without this option the refinement would almost always arrive truncated and fall back.
   - The option is opt-in and capped at 4096, and only the refinement uses it (3000). Default request bodies are unchanged.
   - Even with it, a slow provider may hit the 15 s timeout on a 3000-token answer. The fallback handles that, but in practice refinement may rarely succeed. Consider a longer timeout for the strong tier.
6. **Refinement acceptance is strict.** Every rule must survive word for word (whitespace aside), with its number. A model that reformats the rules as `1)` or `**1.**` is rejected. This is deliberately conservative.
7. **Two `/api/fix` calls per demo** (L1 and L2). With `MODEL_STRONG` set, each refines on its own, so the L2 prompt could differ from the L1 prompt (temperature 0 makes this unlikely). Without `MODEL_STRONG`, they are identical. The UI could reuse the L1 prompt and only switch on the guard.
8. **Edge cases in protected-value handling:**
   - An owner asset that is a common word (for example "code") also appears in the fixed rule text. Refinement is then always rejected (safe), and `containsProtected(fix.systemPrompt)` is true because of the rules, not the owner's text.
   - The letters-and-digits normalisation false positive from T002 open question 6 also applies to `stripProtected`.
9. **Self-check cost and latency:** L2 adds up to one `MODEL_JUDGE` call per step (skipped when (a) already blocked). A step can now make 3 LLM calls (bot, self-check, judge): up to 45 s, within `maxDuration = 60`. `/api/fix` has `maxDuration = 30`.
10. **Refusal wording:** the Urdu refusal avoids a gendered first-person verb («اس درخواست میں مدد ممکن نہیں … مدد حاضر ہے»), so it fits any bot persona. Please have a native speaker check it, along with the new Urdu change texts in `rules.ts` and `deterministic.ts`.
